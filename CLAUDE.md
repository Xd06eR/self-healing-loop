# Self-healing loop framework — development guide

> **You are working on the self-healing loop framework.** This is the dev guide: what the framework is, how it's structured, the hard lessons, and how to test it. Doc split: this file = dev guide · `AGENTS.md` = symlink to it · `README.md` = human overview · `SKILL.md` = installer · `loop_context/CLAUDE.md` = the operating doc copied into a target for the loop's own agent.

## What this framework is (one paragraph)

A skill + portable core that installs a fully autonomous self-healing loop into a target project's own repo: a GitHub Actions cron watches the target's logs; on a real failure a headless agent (a separate `claude -p` / `opencode run` / etc.) diagnoses it, writes a red reproducing test, fixes the source, gates, opens + reviews a PR, merges, deploys, verifies, and records an incident — no human in the happy path. Universal across harnesses and models (the harness is data; the model is a config string). Two load-bearing intents: **no human in the happy path**, **no token-burn thrash** (bounded prompts, structured output, attempt cap, a job timeout, and one cycle at a time per branch).

The repo is named `self-healing-loop`, matching the skill's `name:` and the `SHL_*` env prefix: that name is what an operator types to invoke the installer, so anything else splits one identity across three places. There is deliberately no local simulation of the workflow — see L2.

**File-naming case: uppercase means a person opens it first, lowercase means the machine loads it on demand.** `reference/`, `templates/`, `artifacts/`, `workflows/` and the Python are all loaded by something, so all lowercase. The exception is not a softening: `SKILL.md`, `README.md`, `CLAUDE.md` and `AGENTS.md` are spellings an external convention fixes — a harness auto-loads two of them by exact name — so this project does not get to choose their case.

`artifacts/` is the rule's own worked example, and the reason it is a rule rather than a habit. The same content changes case on the way out because its reader changes: `setup.md` is machinery the installer reads, `SETUP.md` is a document someone opens. `tests/test_file_naming.py` pins all of it, including that a template renamed without its write-out target fails.

## Architecture (condensed)

- **Two seams, one fixed core.** The core (loop + guardrails + structured-output parser) never changes. Two adapter seams fit any target + any harness:
    - **TargetAdapter (per target)** — `read_log` required; `failing_tests`, `failure_ids` and `health_check` optional. `None` means "fall back to what the framework does by itself", and what that is differs per method: `failing_tests` reverts the gate to the strict all-green rule, `health_check` leaves the workflow relying on the suite alone, and `failure_ids` falls back to built-in Python/V8 parsing, which on a Go or Ruby target yields nothing at all. Returning `None` there to mean "cannot answer" silently selects a parser that cannot read the log; `unfingerprintable` then refuses the cycle in `watch.yml` rather than healing blind. A new target is a new adapter, not a new pipeline. `read_log` reads wherever the target's failures surface (a log on disk / the host's logs / the browser only, via a relay / CI going red). Which one is **asked** in the Phase 2 interview, never inferred: a wrong answer here is invisible. It deliberately does NOT deploy or roll back: the workflow runs the operator's `SHL_DEPLOY_CMD` (which may carry deploy credentials no agent-adjacent module should hold) and reverts with `git revert`. Adding abstract `deploy`/`rollback` methods here would force every installer to write two implementations nothing calls.
    - **AgentAdapter (per harness)** — a harness is **data**: one `HarnessConfig` (install, argv template, per-role restriction flags, the verification it offers, model env vars, auth/base-url env) + one `render()`. Restriction is argv; verification carries two seams, because a harness that keeps its restriction in a config file has no argv for the guard to read. Adding a harness = authoring a config, zero framework code.
- **The loop:** Watch → Triage (compact log; idle if nothing) → Diagnose (read-only agent) → Red+Freeze (write repro test, prove RED, freeze) → Fix (source-only agent, no shell) → Gate (in refusal order: loop tree untouched **first**, workflows untouched, `.gitattributes` untouched, no test weakened, no test-config touched, then — only when a frozen test exists — frozen untouched and its neighbours untouched; plus no NEW failures) → PR → Review (read-only agent) → Merge → Deploy (only when the target has a deploy command) → Verify (always; auto-revert on regression) → Record (incident memory, committed). Verify is deliberately not gated on `SHL_DEPLOY_CMD` (reason at the step). The suite half of Verify runs on every ref, but the `health_check` probe runs **only on the default branch**: `SHL_HEALTH_URL` names one deployment, so probing it from a branch cycle reads a different commit and reverts a correct fix as a regression. A per-ref URL does not fix that, since preview deployments are commonly behind authentication and answer a probe with a redirect.
- **Running a harness in the cloud:** a GitHub Actions runner is a disposable PC; a step installs the harness, invokes it headless, authenticates via a repo secret. Each role runs under a pre-authorized restriction, and a harness that cannot prove its restriction refuses to run at all. The framework never uses a harness's full-access escape hatch.
    - **`claude-code`** restricts through argv: Diagnose and Review read-only, Fix editing files with no shell, and **every** role denying `Bash,WebFetch,WebSearch,Agent,Edit(./**)` — the shell, both egress paths, spawning a subagent whose own frontmatter could carry a different permission mode, and writes anywhere in the loop's own tree. The deny set is what restricts, not the mode: a deny rule is the only thing a permission mode cannot override.
    - **`opencode`** has no read-only flag, so restriction lives in per-agent `permission` blocks in `opencode.json`, selected by `--agent`. Rules are last-match-wins: each agent opens with `"*": "deny"` and allows back only what the role needs, Fix's `edit` scoped to deny `**/.shl/**` last so the loop tree wins. `external_directory` is set explicitly on every agent because its default is `ask`, and a headless `ask` never returns.
    - **Verification differs because the two express restriction differently.** A harness declares an argv-shaped `required_denial`, checked against the rendered command line, or a per-role `preflight_argv` that must exit 0. OpenCode needs the second: its denial is in a file, and `run` treats an unresolved `--agent` name as a warning and continues under the unrestricted default, while `debug agent` exits non-zero on the same input. A harness offering neither cannot run any role.
- **Choosing a model:** a config string (`--model` / `ANTHROPIC_MODEL`) + a provider credential (+ base URL when non-native). Third-party models are the primary path.
- **Guardrails (lean + memory):** deterministic gate (the real merge gate), red-then-green frozen test, attempt cap (2 then escalate), confidentiality scrub, post-deploy health + auto-rollback, incident memory (read before every Diagnose), separation of duties (Fix never reviews itself), state in GitHub (not the runner).
- **The reviewer's `reason` is published on either verdict.** It is the field every role is told to report prompt injection in, so reading it only when the fix is BLOCKED means an approval that flags an injected log reaches nobody — while the `issue_body` carrying that injection travels on into incident memory and is replayed into every later cycle matching the same failure. Both paths now scrub it and comment it on the PR. The evidence bundle holds a copy either way, and that is a second copy rather than the channel: an artifact nobody downloads on a green cycle is not where a warning gets read. A failed comment warns instead of blocking, because refusing to ship a fix that passed both gates trades a real merge for a cosmetic one.
- **Every gate verdict states its grounds.** A refusal names the check, the file and the evidence (`BLOCKED [no test weakened]: tests/x.py: assertion removed: assert f() == 1`); a pass names the checks it rested on. The predicates return the violation rather than a bare boolean, so the CLI has something to print, and `None` stays falsy for every truthiness caller. Without this an empty `gate.txt` means both "passed" and "blocked", which makes the must-pass verification unreadable: the operator sees a red step and no cause, and the evidence bundle cannot distinguish an approval from a gate that never ran.
- **The adapter reads the whole `vars` context, not a per-variable allowlist.** Workflow templates can only name the `SHL_*` variables the framework knows about, so a variable an adapter invents is correctly set in the repo and absent at runtime — and hand-added `env:` lines are silently dropped by the next re-vendor. `SHL_VARS: ${{ toJSON(vars) }}` plus `adapters.hydrate_repo_vars` deletes both failures instead of detecting them; explicit entries still win, and `secrets.*` is a separate context that never travels this path. Hydration is confined to the `SHL_` namespace and skips `SECRET_ENV_VARS`, for two different reasons: `vars` carries organization-level variables inherited by every repo in the org, so an unfiltered fold would let an unset `NODE_OPTIONS` or `GIT_SSH_COMMAND` set org-wide change how this loop's subprocesses run; and a provider token stored as a variable rather than a secret would otherwise be delivered into the one step built to run without it. A blob that is present but unreadable raises rather than degrading, because degrading quietly reinstates the exact failure the mechanism exists to remove.
- **Fix may add regression tests, and that grows the suite the gate rests on.** Taken deliberately rather than inherited: a fix without regression cover is a worse fix, so the alternative costs more than it saves. What it means is that a merged cycle can add assertions the fixing agent wrote, reviewed by the Review role and by whoever reads the PR. The gate encodes the same split — `is_test_helper_touched` refuses *modifications* beside the frozen test and excepts *additions* — so `templates/fix.md`, `loop_context/CLAUDE.md` and the gate all draw the line at the same place: add freely, never edit what exists.
- **The gate asks two separate questions**, and they must stay separate: *is the bug fixed* (the frozen reproducing test flips red to green) and *did the fix break anything* (`gate.new_failures`: no test that was PASSING now fails). Answering both with one all-green check makes a single pre-existing failure veto every correct fix, which is unusable on any real repo. Baseline failures come from the optional `TargetAdapter.failing_tests()`; adapters that do not implement it keep the strict all-green rule.
- **Log compaction keeps one slot per distinct failure** (`log_compact`), not a raw tail cut. A health check that 500s on every page render otherwise buries a rarer bug under dozens of identical tracebacks and the tail cut drops it entirely, so the loop never sees it and never heals it. Repeats collapse to their most recent occurrence plus a count. Three things make "distinct" mean what it should: a chained traceback is ONE block (the intermediate exception before `During handling of the above exception` is a library step, not the failure), the identifying frame is the deepest one the PROJECT owns rather than the deepest overall (two unrelated bugs both bottom out at the same line of starlette and would otherwise be one failure), and truncation drops whole blocks rather than slicing mid-traceback (a sliced traceback loses the frames that give it an identity).
- **Every failure identity is derived from the RAW log, never from the compacted signal.** The two views are not interchangeable and the split is load-bearing: compaction keeps error lines plus their INDENTED continuation, and a Go panic puts its trace behind a blank line and indents none of it, so identifying from compacted text hands `TargetAdapter.failure_ids` a message with no frames — on precisely the runtimes that method exists to serve. It returns `[]`, `unfingerprintable` reports the failure unreadable, and the cycle is refused on every tick forever. So `loop.py watch` takes a path and writes the log as read; `fingerprint-marker`, `find-issue`, `recall_incidents` and `record_cycle` all read that file, and only the agent's prompt gets the compacted signal. A missing raw path is refused rather than defaulted to the signal, because that default is silent and reinstates the whole defect. Pinned at the workflow as well as in Python: the Python keys correctly on whatever it is given, so the only place the defect can live is the argument, and that is a seam no unit test crosses.
- **Incident memory matches on failure fingerprints, never on the issue title.** `log_compact.failure_fingerprints` derives `ExceptionType@path:line` from the same raw log on both sides, so an identical failure keys identically; paths are made repo-relative so an incident recorded on a laptop still matches on a runner. Keying on the title cannot work — it is prose a model writes fresh each cycle. Exact-set intersection is also the primary defence against context pollution: an unrelated incident never enters the prompt however many accumulate, and `loop.MAX_RECALLED_INCIDENTS` / `MAX_ROOT_CAUSE_CHARS` cap the pathological case where one failure recurs dozens of times, reverted incidents ranked first so a cap never drops a KNOWN-BAD warning. The store itself is bounded too: `record_incident` prunes to 500 records once over the cap, rewriting only then so the normal path stays an append and each incident commit stays a one-line diff. A `reverted` record is exempt at any age, because it is the one thing telling a later cycle that the obvious fix was already tried and made things worse.
- **Evidence (`evidence.py`):** each role writes its exact prompt, raw output, stderr and metadata to `.shl/evidence/<cycle>/`, alongside the cycle's signal, diff, gate and suite output. Scrubbed identically local and cloud; uploaded as an Actions artifact under `if: always()`, so a cycle that dies at the gate still ships its evidence. `SHL_CYCLE_ID` (the Actions run id) pins all three role processes to one dir; locally Diagnose opens a UTC-timestamped dir (`YYYYMMDD-HHMMSS`) and Fix/Review join the most recent one, which is why that format must keep lexicographic and chronological order identical. Two invariants pinned by tests: env VALUES never reach disk (only key names — that dict holds the provider token), and the prompt is not duplicated into the metadata.

- **Auto-merge is unconditional, and a PR-only mode was considered and rejected.** The obvious objection is real: responsibility does not transfer, so a machine merging to the default branch unattended is exactly the authority you would normally keep. The reason it stays is structural rather than philosophical — `heal.yml` runs Merge → Deploy → Verify → Rollback → Record as sequential steps in one job, so skipping the merge amputates post-deploy verification, auto-rollback and the incident record along with it. A PR-only loop trades the safety net and the memory for a button, and what is left is a diagnose-and-propose bot, not a self-healing one. What the objection actually points at is narrower and is covered: on a protected default branch with no bot bypass, every cycle burns three agent calls and then dies at merge, so that is a Phase 0 blocking check. Operators who cannot accept unattended merges set `SHL_DEPLOY_CMD` empty and keep the loop off that service, which the residual-risks section already documents.
- **The installer is a consultation, not an inference engine.** `SKILL.md` determines what the repo can answer, interviews the operator about everything else one question at a time, and writes nothing until they agree. There is no headless path: without an operator it stops and reports why. It also invokes no other skill, because it installs onto machines configured nothing like this one, so any skill it called would be a dependency that is missing. The rule dividing the two tiers: **a fact may be determined only if getting it wrong would be visible.** A wrong test command dies loudly, so it is determined; a wrong log surface makes the loop idle, and idle is indistinguishable from healthy, so it is asked. The same rule is why the deploy target is never inferred from config: a PaaS connected through a Git integration leaves nothing in the repo to sniff.

    Two things settled the tier split rather than taste. Fitting a loop to one small, well-understood project took hours of dense conversation about where failures surface, whether the app should gain a backend, retention versus cron cadence, and what the gate rests on — none of which is a lookup. And installing writes **product code** into the operator's repo: a test suite that becomes the gate guarding the default branch, and possibly a public endpoint. A rubber-stamped table is not consent for either.

Full env contract + per-stage detail: `SKILL.md` + `artifacts/setup.md`. Branch-specific installer detail: `reference/`.

## KEY LESSONS (read before touching anything — expensive past mistakes)

- **L1 — this tree is read-only during testing.** Never write test artifacts into it. All test work lives in scratch. The framework is the product. Note the way this one hides: running `loop.py` or `evidence.py` from here creates `.shl/evidence/<cycle>/` beside them, and if the cycle wrote nothing the directory stays **empty** — which git does not track and `git status` therefore reports as clean. A clean status is not evidence that nothing was written.
- **L2 — Never build a second driver; run the shipped one.** The loop's agent is a SEPARATE cold `claude -p`, so use the framework's OWN entrypoints (`loop.py`'s `run_diagnose` / `run_fix` / `run_review`, which spawn real cold subprocesses). This project once kept a local harness that reimplemented `heal.yml`'s step sequence in Python; it reported every path green while the shipped workflow could not complete a single cycle on a runner, because it never invoked the CLI the way the workflow does. It has been deleted and nothing replaced it: the sequence is proved only by running the real workflow against a real repo. A parallel driver tests the driver, not the framework.
- **L3 — Never pre-feed discovery answers to the installer.** Phase 1 determines what the repo can answer for itself; Phase 2 ASKS the rest. Pre-feeding "no runtime log" produced a wrong adapter that read the test suite instead of the real log, and pre-*building* the answers (a hand-written suite and relay) would have been worse: the installer would have been handed a finished job and passed while proving nothing. Answering the interview honestly as the operator is not pre-feeding; volunteering the conclusions is.
- **L4 — A failure the log never records does not exist to the loop.** Many apps wrap handlers in `try/except`, so a caught bug returns 200-with-error, writes nothing, and the loop idles looking healthy. When seeding a bug for the self-test, put it OUTSIDE that boundary (a dependency getter, middleware, `/health`). The generalisation is the visibility rule that now governs the whole install.
- **L5 — Never run the loop against a tracked copy of the target.** Every heal cycle mutates the target: the fix and its reproducing test land in tracked files and have to be policed out of every commit. Testing in place was tried and abandoned. Use a scratch clone, or a real repo the loop is genuinely installed into.
- **L6 — "Never commit" binds the DEVELOPING assistant, not the loop.** Working *on* this framework, output git commands for the operator to run. The loop itself commits, pushes, opens PRs, merges and reverts autonomously — that is the product, not a violation of the rule. The installer likewise commits its own install to a branch and opens a PR, because `workflow_dispatch` cannot see a workflow that was never pushed. Conflating the two produced an installer that wrote files nobody could run.
- **L7 — Logs are not always in the project folder, and where they are cannot be inferred.** Some live on the host (CloudWatch, Sentry, Vercel/Railway/Fly, journald), and a PaaS connected by Git integration leaves NOTHING in the repo to sniff. This is decision 2 of the interview, asked and never guessed: a wrong answer makes the loop read the wrong place, find nothing, and idle, which is indistinguishable from a healthy project.
- **L8 — A test that never uses real data can pass while the feature is dead.** Incident memory had four green unit tests for months and recalled nothing, ever: every test queried `search_similar` with a short hand-written string like `"zerodivision"`, while production passed a raw log line (a stack frame, or an access-log line carrying an ephemeral port) matched by substring against a model-written title. The tests encoded the intended contract instead of the real one. For anything whose input is produced by another part of the system, drive at least one test with a genuine captured artifact.
- **L9 — Calling the function is not running the loop; verify at the seam the product uses.** After fixing L8's key, `recall_incidents` was confirmed correct against real captured signals — and the very next live cycle still printed *"no prior incident for this signature"*, because the local driver derived the lookup key itself and had not been updated. Every claim about the loop must be proved from a cycle's evidence bundle (`diagnose.prompt.txt`), never from a direct call. **This was the third time the same drift shipped**, after the baseline step running in the wrong order and the record step being built twice. The durable fix is structural, not vigilance: `run_diagnose`/`run_fix` now compute the recall themselves and no longer accept it as a parameter, so a driver cannot supply a wrong one. When two drivers must do the same thing, give them one function to call rather than one rule to follow.
- **L10 — A vendored copy is stale until proven otherwise.** The target holds a COPY of the core, so a framework fix does nothing there until re-vendored, and a cycle run against the old copy reports a confident, wrong result. This produced a false "verified" more than once — most sharply when a freshly-built collapse feature was declared working after a cycle whose vendored `loop.py` did not contain it. The driver that used to auto-refresh the vendored copy is gone with the rest of the local scaffolding, so re-vendor after any framework change before drawing any conclusion from a target, and never hand-copy. The *detector* is the update procedure in `reference/updating.md`: `.shl/manifest.json` records a hash per vendored file, and the update compares it against both the installed files and the framework to tell stale from locally modified. It runs when someone takes the update branch — nothing runs it on a cycle — so the habit above still stands, and the manifest answers "is this copy current", not "is it correct".

## How to test

Two different activities, and keeping them apart is a product decision, not bookkeeping. **Development testing** verifies this framework and is ours. **Installation testing** verifies one installed loop, belongs to that loop's operator, and is optional — the installer writes no deliberate defect into anyone's repo, because proving a loop heals needs a failure and manufacturing one is the operator's call. Its procedure is `reference/verifying-the-install.md`, which the installer offers and never runs.

Development testing:

- **Unit tests:** `PYTHONPATH=. python3 -B -m unittest discover -s tests -v`, run from the directory holding `SKILL.md` — all green, or the change is not done. Anywhere else it exits `ImportError: Start directory is not importable: 'tests'`. That directory is named rather than called "the repo root" because the two coincide only once this ships as its own repo, and the instruction has to be right in both cases.
- **Install `actionlint`, or the workflow templates go unchecked.** The suite's Actions-schema check is guarded by `shutil.which`, so without the binary it skips and the run still reports `OK` — and a real defect in `heal.yml` or `watch.yml` flips from caught to `OK (skipped=2)` purely on `PATH`. The skip is deliberate: hardening it into a failure would break the stdlib-only promise for anyone running the suite on a bare Python. So the binary is the developer's responsibility, and `actionlint -no-color -oneline workflows/*.yml` is a required manual step before any release. Nothing else validates the two files that *are* the product.
- **The real thing:** install into a repo with `SKILL.md` and drive a full cycle against it. There is no local simulation any more, on purpose (L2).

**What actually backs this code, stated because the green suite overstates it.** Two partial cycles have run on real runners against real failures, and both predate substantial rewrites of the gate, `guardrails/cli.py` and `heal.yml` — so they evidence the design, not this tree. No cycle has ever completed. Everything from the merge onward, the gate refusing a bad fix, the attempt cap, the escalation path and OpenCode as a harness are covered by unit tests and by nothing else.

That makes mutation the load-bearing discipline rather than a nicety: a suite with no integration test behind it is only as good as its ability to fail. The git-surface guard is the worked example — it shipped a defect that made every cycle refuse, and the suite was green with the defect present *and* with it removed. Plant the defect, watch the suite go red, and assert the unmutated control exits 0 first, or the run proves nothing.

**Prose is not testable, and a check must never pretend otherwise.** Every shipped reader-facing document — `SKILL.md`, `reference/`, `artifacts/`, `templates/`, `loop_context/CLAUDE.md` — is bound by the current-fact convention: no session narrative, nothing phrased relative to an earlier version, no anchor a later reader cannot resolve. Nothing in the suite enforces it, and nothing in the suite can. Whether a document assumes context it does not supply is a semantic judgement; a regex matches a fixed vocabulary of tells and no more.

So a check named for that convention while implementing the vocabulary is worse than no check, because it reports coverage of a rule it does not hold — this project's signature defect turned on its own tests. A mechanical guard is legitimate only for mechanical leaks: a date, a specific target repo's name, stage or session numbering. It is named for exactly those and never for the convention.

The convention is verified the one way it can be — a fresh context reading the document with no history. For `SKILL.md` that is not an extra step, it is already the install's acceptance criterion: the interview must reach the right conclusions without being led. The same rule binds any doc-to-code agreement whose subject is meaning rather than a token: pin what is mechanically checkable, state the ceiling, and send the rest to a reader who was not there.

## Known residual risks (honest)

- **Fix runs with cwd `.shl/`, which is the loop's own code**, and two things keep it out that a tamper cannot reach: whichever harness is running denies edits there (`Edit(./**)` on Claude Code, an `edit` deny on `**/.shl/**` on OpenCode), and a `git`-only workflow step runs immediately after Fix, before anything imports from that tree. `gate.is_loop_tree_touched` covers the same ground, but it is imported FROM the tree it judges, so it cannot catch a tamper against itself — a third check, not a second control. Moving Fix to the repo root would not help: `.shl/` sits inside the repo root, so an edit-permitting mode auto-approves it either way. A cwd-relative deny is what closes this, not a cwd change.
    - **That step asks git two questions, and needs both.** `git diff` reports modified TRACKED files only, so creation is invisible to it — and creation is the cheaper tamper, because an interpreter started with `.shl` on `PYTHONPATH` imports `.shl/sitecustomize.py` at startup, before `-m guardrails.cli` loads, and `-B` disables bytecode rather than `site`. The vendored `.gitignore` covers scratch, not `*.py`, so such a file would be committed and run every later cycle. `git ls-files --others --exclude-standard` answers the creation half and honours that same `.gitignore`, so ordinary cycle scratch stays quiet.
    - **Its position is load-bearing.** Nothing that imports from `.shl/` may run between Fix and this guard — by `PYTHONPATH`, a changed cwd, or a script path, the three forms `heal.yml` uses — or the tamper executes before the check that would have caught it. The `.shl`-importing invocations earlier in the job — the harness-install probe, `find-issue`, the two issue scrubs and the fingerprint marker, five in all — sit upstream of Fix, so nothing is planted for them to execute; without that qualifier a reader who counts them finds five apparent violations and no way to tell whether the rule or the workflow is wrong.
    - **It asks a third question, for the same reason as the other two.** `.git/config` and `.git/hooks/` are executable by git itself, live outside every diff, and are therefore invisible to `gate.py` and to the Review agent alike. The step compares them against a hash taken immediately before Fix and published as the pre-Fix step's output — a later step cannot rewrite a completed step's outputs, whereas `$RUNNER_TEMP` is outside the checkout but not outside the agent's write reach, and the tamper's own payload runs during the guard step, early enough to rewrite a file record. The comparison also runs before the guard itself calls git, since `core.fsmonitor` executes on the next git invocation and would otherwise fire, restore the config, and erase the evidence of itself.
        - **What it does not reach, accepted rather than closed.** Three gaps, all verified rather than reasoned about, and none closed — because every candidate fix is a claim about runner behaviour, and a guard that fails closed on every cycle blocks the loop entirely while looking like a working check.
            - **Git also takes executable configuration from the ENVIRONMENT.** `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_*=core.hooksPath` runs a hook from an attacker path, and `GIT_SSH_COMMAND`, `GIT_EXTERNAL_DIFF` and `GIT_PROXY_COMMAND` each name a program git executes — none of which touches a file this block hashes. Fix reaches that surface by appending to its own `$GITHUB_ENV`, which applies to every later step, including the one running `git push` under `GH_TOKEN`. Comparing env between the two steps would catch it, but the two blocks run in different steps and env is not reliably identical across that boundary; hashing the `$GITHUB_ENV` *path* is precisely how this guard once refused every cycle on every repo.
            - **The baseline is measured after untrusted code has already run.** Diagnose's reproducing test executes under the target's test runner, with a full shell, before the snapshot is taken. A hook that test plants is therefore already in the baseline, and the guard compares tampered against tampered. Moving the snapshot earlier is the fix and is unverified.
            - **The hooks measurement is bounded by what `find` can see.** Symlinked hook *files* are measured; a `.git/hooks` **directory** replaced by a symlink is not, because `find` does not follow a symlinked start point.
- **`actions/checkout` stays on v5 deliberately, and the reason is the guard above.** v6.0.0 moved the persisted credential out of the local git config into `$RUNNER_TEMP`, leaving `.git/config` pointing at it through an `includeIf`. An included file IS git config — it can set `core.hooksPath` — so the bump converts a fully measured config surface into one where a third config file sits unhashed, in a directory this workflow already documents as writable by the agent. Closing that means hashing a runner-allocated path across a step boundary, which is precisely the shape that once made this guard refuse every cycle, and no runner exists to tell anyone whether it holds. The usual argument for upgrading does not apply: **v5 is already Node 24** (`using: node24` on the v5 tag; the runtime move *is* v5.0.0's headline change), the pin floats so v5.1.0 picked up the same `allow-unsafe-pr-checkout` security backport v6 and v7 got, and v7's own headline is an ESM migration against a step whose wall time is network-bound. Risk of moving is silent, benefit is zero. Re-open it only if v5 stops receiving backports.
- **Both harnesses install a pinned version, and nothing bumps them.** The runner installs the harness fresh every cycle, so a floating spec makes the loop's behaviour a function of the date: a cycle that worked yesterday breaks today with nothing in the tree to explain it, which is the one failure mode this project's whole diagnostic story cannot absorb. What breaks across harness releases is exactly what the framework rests on — argv flags and permission semantics — and `--max-turns` has already been removed from one of these CLIs. The cost is real and accepted: upgrading is a manual edit, and a pin left alone for a year is a harness a year out of date. `tests/test_harness.py` refuses an unpinned spec so this stays a choice.
- **`actions/setup-python` tracks the latest major; `upload-artifact` and the harnesses do not.** The asymmetry is about blast radius rather than a policy. setup-python fails loudly and early — no Python, the job dies at step two — so taking its silent-manifest-fetch fix costs a loud risk for a quiet one. The artifact action and the harnesses can each fail in ways that look like something else, so they move only deliberately.
- **The scrubber's shape patterns cannot cover every provider.** Literal-value redaction of `SECRET_ENV_VARS` closes that for secrets the process holds; a secret it does not hold is still shape-matched only.
- **A single agent call is bounded by wall-clock only, not by spend.** The job timeout is the hard stop; there is no per-invocation turn or cost cap, deliberately: `--max-turns` does not exist in this CLI, and `--max-budget-usd`, which `claude --help` does list, was rejected rather than tested. Against a third-party base URL the CLI has no pricing for, a cap that computes nothing would read as a bound while being none, which is this project's signature defect class wearing a safety label. `--bare` was rejected for the same shape of reason: it wants `ANTHROPIC_API_KEY` and never reads the keychain or OAuth, while the primary path authenticates with `ANTHROPIC_AUTH_TOKEN` + `ANTHROPIC_BASE_URL`, so adopting it unverified risks breaking the very path most installs use.

- **Fingerprinting reads Python and V8 stacks itself, takes anything else from the target, and refuses what neither can identify.** A Go, Ruby, Rust or Java traceback yields no `Type@path:line`, which leaves issue dedup, incident recall and the attempt cap keyed on nothing — the same failure re-diagnosed every tick with the cap never accumulating. Two things close it. `TargetAdapter.failure_ids` lets the target supply the identity, resolved through `adapters.optional_ids_fn` by every consumer so the marker, the recall and the record cannot key differently, and handed the RAW log because the frames it keys on do not survive compaction. And `log_compact.unfingerprintable` separates a log with no failure (ordinary idle) from a log whose failure could not be read (a coverage gap), stopping the second in `watch.yml` before any agent call is spent. What is not closed: nothing checks that a supplied identity is stable or specific, so an adapter returning one string for every failure collapses unrelated bugs into one incident.
- **The gate's language knowledge is installer-supplied, and unsupplied means unpoliced.** Test-file globs, runner-config globs, and what an assertion and a skip look like all arrive as `SHL_*` values, each ADDED to a built-in describing Python and JS rather than replacing it, so setting one cannot disarm another. That covers any stack the interview asks about, and it moves the failure from "the check silently passed everything" to "nobody told the check what to look for" — better, but still quiet. One check closes part of it: the gate proves the supplied assertion pattern matches something in the frozen reproducing test, and refuses when it does not, so a pattern that recognises nothing cannot police nothing. **That proof hangs off `--frozen`, which the workflow supplies only when Diagnose could reproduce the failure** — the minority of cycles by the prompts' own account — so on most cycles it does not run at all, and `cli.py` says so in the pass line rather than letting the silence read as a check that passed. What remains open is the rest of the suite, where a wrong regex still polices the wrong thing as confidently as a right one. The built-in config list covers Python, JS, and the Ruby, Rust and JVM manifests, and `tests/test_prompt_contract.py` pins docs and globs together in the direction that fails open: a doc may not name a config file the compiled globs ignore, nor call one unpoliced that they match.
- **Freezing the reproducing test does not freeze what it imports, and the remedy has to know the layout.** `is_frozen_test_touched` matches one path and `is_test_weakened` inspects only test-glob matches, so a helper beside the frozen test is neither: neuter it and the frozen test goes green with the bug intact. `is_test_helper_touched` closes the common case by refusing any modification to a pre-existing file in the frozen test's directory, additions excepted because Fix legitimately writes regression tests there. It applies only where that directory is named as a dedicated test tree, because a layout that puts tests beside source — Go's `thing.go` next to `thing_test.go` — would otherwise refuse every legitimate fix. **Where it declines, the pass line says so**, since a check that quietly did not apply reads exactly like one that ran. What remains open: a helper outside that directory, and every mixed layout. The gate is line-based more generally, so a semantic rewrite of a *non-frozen* test dodges it too; AST-diff is the upgrade for both.
- Red-then-green covers reproducible failures only; non-reproducible ones lean on gate + review + rollback.
- Rollback restores code, not external side effects a bad deploy already took.
